# WebAssembly entrypoint

`cmd/wasm` builds the library into a WebAssembly module a browser (or any
JS host) can load directly — no local Go toolchain needed. It is thin glue
only: all real logic lives in the root `snd` package (see
[docs/api.md](api.md)), which is unit-tested independently of this file.

## Building locally

```sh
GOOS=js GOARCH=wasm go build -o snd.wasm ./cmd/wasm
cp "$(go env GOROOT)/lib/wasm/wasm_exec.js" .
```

`cmd/wasm/main.go` is build-tag gated (`//go:build js && wasm`), so it is
invisible to a normal host build/test — `go build ./...` and `go test ./...`
never touch it.

## JS API

The module registers a single global on `js.Global()`:

```js
globalThis.OpenKakutouSnd.decode(sndBytes, group, sample, resolveExternal)
```

- **Arguments**:
  - `sndBytes` — a `Uint8Array` — the raw bytes of a `.snd` file (v1 or v2,
    auto-detected), already fetched or selected by the caller.
  - `group`, `sample` — numbers identifying the sound to decode, the same
    `(group, sample)` addressing a character's own sound-triggering
    controller uses.
  - `resolveExternal` — optional. A v2 sound can point at an external audio
    file instead of embedding its samples (Ikemen GO's own extension). When
    the decoded entry turns out to need one, `resolveExternal(path)` is
    called **synchronously** with that relative path and must return a
    `Uint8Array` of the file's bytes directly — it cannot be `async`, return
    a `Promise`, or fetch the file lazily. The caller must already hold the
    external file's bytes (typically preloaded the same way `sndBytes`
    itself was) before calling `decode`. Omit it, or pass `undefined`/`null`,
    when no external references are expected — matching an ordinary embedded
    sound, this is the common case.
- **Return value**: always a plain object
  `{ sampleRate, channels, bitsPerSample, pcm, error }`, exactly one of
  `pcm`/`error` non-`null` (the numeric fields are `0` on error, not
  `undefined`):
  - `pcm` — an `Int16Array` of the decoded audio, interleaved by channel and
    always normalized to signed 16-bit regardless of the source's original
    bit depth — ready to feed into the Web Audio API.
  - `error` — a descriptive message (an unrecognized file signature, an
    unknown `(group, sample)`, a missing/invalid `resolveExternal`, or the
    reason the call itself was malformed, such as a wrong argument count).
- The function never throws: an internal panic is recovered at this
  boundary and reported as `error` instead of crashing the whole page's
  WASM instance. A prior error does not leave the module in a broken
  state — the next call is handled independently.

### Example

```js
const result = globalThis.OpenKakutouSnd.decode(sndBytes, 0, 0);
if (result.error) {
  throw new Error(result.error);
}
playPCM(result.pcm, result.sampleRate, result.channels);
```

With a v2 sound that may use the external-file-reference extension:

```js
const result = globalThis.OpenKakutouSnd.decode(sndBytes, 0, 7, (path) => {
  return preloadedAudioFiles.get(path); // must already be in memory — see above
});
```

## Verifying a build

`cmd/wasm/smoke.mjs` is a Node.js harness that loads a built module the same
way a browser would (via `wasm_exec.js`) and exercises the nominal path
(both versions, auto-detected), the external-file-reference path, and error
paths — the closest thing to `go test` this file has, since `syscall/js`
code cannot run under the plain Go toolchain:

```sh
node cmd/wasm/smoke.mjs [path/to/snd.wasm]  # defaults to ./snd.wasm
```

## Release pipeline

`.github/workflows/release.yml` runs on every pushed tag matching
`v[0-9]*.[0-9]*.[0-9]*` (e.g. `v1.2.3`). It builds and tests the module
normally first (`go build ./...`, `go test ./...`, `go vet ./...`) — nothing
is published if any of those fail — then builds `snd.wasm` and copies the
matching `wasm_exec.js`. Before publishing, it also runs `cmd/wasm/smoke.mjs`
against the exact just-built `snd.wasm` bytes on a pinned Node.js version,
gating the release on a real, working WASM artifact rather than only a
successful native build. Only then does it publish both files as assets on
that tag's GitHub Release under stable, predictable names. `wasm_exec.js` is
Go-version-specific glue; the workflow always builds and copies it from the
same Go toolchain install that produced the `.wasm`, so the two published
files are guaranteed to be a matched pair — a consumer should always fetch
both from the same release, never mix versions, and never mix them with
another repo's own `snd.wasm`/`wasm_exec.js` pair either.

See
[`.vibe/decisions/004-wasm-entrypoint-api-shape-and-version-detection.md`](../.vibe/decisions/004-wasm-entrypoint-api-shape-and-version-detection.md)
for why the API is shaped this way (mirroring the sibling `sff` project's
own WASM entrypoint contract, adapted for this format's single decode
operation).
