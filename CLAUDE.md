## Project overview

OpenKakutou `snd` is a read/write Go library for MUGEN/Ikemen GO sound (`.snd`) files: v1 and v2 parsing and decoding to raw PCM. It is extracted as its own repo from the start (see the roadmap's decision `026-scope-org-wide-audio-snd-and-bgm-support`) because two independent consumers need it: [`character`](https://github.com/openkakutou/character) (a character's own hit/voice/taunt sounds) and [`mode-quick-versus`](https://github.com/openkakutou/mode-quick-versus) directly (system/common sound sets not tied to any one character). It has no playback dependency and must compile cleanly to WebAssembly.

**Stack:** Go 1.26, stdlib-only, compiled to WASM (`GOOS=js GOARCH=wasm`) for browser consumers. No UI code, no audio playback code lives in this repo.
**Type:** library

## Project context <!-- keep -->

This repo is a **shared, domain-independent dependency** of the OpenKakutou org (github.com/openkakutou) — it belongs to no single domain, mirroring [`sff`](https://github.com/openkakutou/sff)'s own shape and role. Its consumers:

- `character` — depends on it (Go module) to decode a character's own `SoundFile` and expose its samples via the WASM `load`/`LoadBytes` contract (see `character`'s backlog item 057)
- `mode-quick-versus` — depends on it (via the WASM build) directly, for system/common sound sets that aren't part of any character's own files, and to actually play back both those and `engine`-triggered character sounds (see `mode-quick-versus`'s backlog item 013)
- `engine` never depends on this repo — it only triggers `PlaySnd` as an event (`(group, sample)`), never decodes or plays audio itself (see `engine`'s backlog item 020 and roadmap decision `004`/`008`, which scope `engine` to simulation, not rendering/asset decode)

Compatibility target (org-wide convention, same bar as every other parser): MUGEN 1.0/1.1 **and** Ikemen GO, validated against real community files — not just the spec. Includes Ikemen GO's own `.snd` v2 extension letting a sound entry point at an external audio file instead of embedding samples.

## Design constraints <!-- keep -->

1. **No playback dependency.** This module only parses `.snd` files and decodes to raw PCM — no `AudioContext`, no SDL2_mixer, nothing playback-related. It must compile cleanly to WASM and be usable as-is by libraries (`character`) and web/native apps (via WASM or direct Go import).

2. **Stdlib-only.** No third-party Go dependencies, matching `sff`'s and `character`'s convention.

3. **Domain-independent.** Nothing character- or game-mode-specific may leak into this repo — it handles the `.snd` file format and PCM decode, period. If a consumer needs something domain-shaped (e.g. mapping a `PlaySnd` controller's `(group, sample)` to an actual playback call), it belongs in that consumer.

4. **Real-file compatibility over spec purity.** `.snd` compatibility should be hard-won through fixture-driven testing against real, unmodified community files, the same practice `character`/`sff`/`stage` already follow (see `sff`'s own `.vibe/fixture-sources.md` for the pattern to mirror). Local machine-specific fixture corpus paths must never be hardcoded into source, tests, or committed config; trimmed fixtures get vendored into `testdata/` instead.

## Development workflow (Vibe Coding)

The user is the **Product Owner only**. They describe requirements and evaluate outcomes — they do NOT write or manually test code.

### Definition of Done

A task is complete ONLY when ALL of the following are true:

- [ ] Implementation code is written
- [ ] Tests covering the nominal path exist and pass
- [ ] Tests covering edge cases and error paths exist and pass
- [ ] Lint exits with code 0 — `gofmt -l .` reports no files, `go vet ./...` is clean
- [ ] All tests pass — `go test ./...`
- [ ] No debug artifacts left in code (`fmt.Println` debug calls, commented-out code, etc.)

**Never present a result to the user if tests are failing.**

### TDD workflow

For every feature or fix:

1. **Write tests first** — describe expected behavior through tests before writing implementation
2. **Confirm tests fail** — run `go test ./...` and verify new tests fail (red)
3. **Write implementation** — minimum code to make tests pass
4. **Confirm tests pass** — run `go test ./...` and verify all tests pass (green)
5. **Refactor if needed** — clean up while keeping tests green
6. **Run lint** — run `gofmt -l .` and `go vet ./...`, fix any issues
7. **Present result** — summarize what was done, what was tested, and the test output

### Bug fix workflow

1. **Reproduce in a test first** — write a failing test that captures the bug
2. Fix the bug
3. Confirm the test passes
4. Present result with the test name that now covers the bug

### Self-correction loop

If tests or lint fail:
- Do NOT ask the user for help
- Diagnose the failure, fix it, re-run
- Repeat until green (max 3 self-correction attempts)
- Only escalate to the user if the failure reveals an ambiguous requirement

## Testing conventions

- Test location: co-located with source, `*_test.go` per package (e.g. `version_test.go` alongside `version.go`)
- Test runner: built-in `go test`
- One test file per source file
- Test names must describe behavior: `TestDecodeV2Sound_ReturnsError_OnTruncatedData`, not `TestDecode`
- Always cover: happy path + at least 2 edge cases + error/invalid input
- Round-trip tests are required for any write-path code: serialize → re-parse → re-decode → compare (semantic round trip; `.snd` is binary, byte-exact preservation is not a goal)
- Decoders/encoders must be validated against real, unmodified community files (vendored as trimmed fixtures in `testdata/`), not only hand-built synthetic data — `sff`'s and `character`'s history both show synthetic-only fixtures repeatedly missed real-file bugs

## Constraints

- Never leave dead code or unused imports
- Never hardcode secrets — use environment variables
- Never skip tests to meet a deadline — fix the code instead
- Style is enforced by tooling, not by convention — always run `gofmt -l .` and `go vet ./...` before presenting results
- No third-party Go dependencies (stdlib-only), and nothing playback-related — see the design constraints above
- Never hardcode a local, machine-specific fixture corpus path into source, tests, or committed config
