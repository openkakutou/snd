# V2 sound-table subheader stores Group and Sample as 4-byte fields, not v1's 2-byte-plus-reserved layout

**Context:** Backlog item 002 asks for a v2 `.snd` read path with "the same shape" as v1's data model. Before writing `ParseV2`, its exact subheader byte layout needed to be pinned down against something authoritative — a written Elecbyte spec for `.snd` could not be found (checked: `elecbyte.com/mugendocs-11b1`, the Wayback Machine's index of that host, and general web search), so the reference was instead the two sources this org already treats as ground truth for real-format compatibility: Ikemen GO's own current loader (`ikemen-engine/Ikemen-GO`, both `develop` and `release/1.0` branches, `src/sound.go`'s `LoadSndFiltered`) and direct inspection of real, unmodified character `.snd` files from the local corpus (`.vibe/fixture-sources.md`).

Ikemen GO's loader reads each subheader as `NextSubHeaderOffset uint32`, `SubFileLength uint32`, then `var num [2]int32` — i.e. Group and Sample are each a full 4-byte signed integer, immediately adjacent, filling the entire 16-byte subheader with no unused bytes. This is applied unconditionally, regardless of the file's declared version — Ikemen GO's loader never branches on the version field at all.

A direct byte-level scan of a real file (`Teenage Mutant Ninja Turtles/Leonardo/TMNT Leonardo.snd`, untouched, from the corpus `.vibe/fixture-sources.md` describes) confirms this independently of Ikemen GO's source: reading bytes 12–16 of several consecutive subheaders as a little-endian `int32` yields a clean, sequential run of Sample values (1, 2, 3, 4, 5, 6, 13, 7, 8) for Group 1 — not the constant 0 that v1's own 2-byte-Sample-at-offset-10 reading would produce for every one of those same entries (bytes 10–12 are actually the upper half of Group's 4-byte value, which is 0 for a small Group like 1).

**Decision:** `ParseV2`'s subheader layout is: `NextSubHeaderOffset` (4 bytes) + `SubFileLength` (4 bytes) + `Group` (4-byte little-endian signed int) + `Sample` (4-byte little-endian signed int) — 16 bytes total, matching Ikemen GO's own reference parser exactly, with no reserved/unused region. This is a deliberate, evidenced divergence from `ParseV1`'s existing subheader reading (2-byte Group at offset 8, 2-byte Sample at offset 10, 4 bytes unread at offset 12), which item 001 shipped and closed before this discrepancy was found.

**This uncovers a likely latent bug in the already-shipped `ParseV1`:** for any real file where a Sample index does not fit entirely within the low 16 bits described above (in practice: any group with more than a couple of samples, since v1's reading of the true Sample field's low half as "reserved" and its own "Sample" field as Group's high half means it will read Sample as 0 for essentially every entry once Group is small — exactly the TMNT Leonardo example above), `ParseV1` likely returns wrong `Sample` values today, silently colliding multiple real entries onto `(group, 0)`. This is out of scope to fix here — item 001 is done and closed, and fixing it is a decision for its own ticket — but it is significant enough to flag explicitly rather than let it go unnoticed. See backlog item created alongside this decision.

**Reason:** The org's own compatibility bar (`CLAUDE.md`, design constraint 4: "real-file compatibility over spec purity") requires validating against the authoritative reference and real files over reconstructing a plausible-looking layout from memory — exactly the principle `sff`'s decision `014` already established for a different format gap. Both independent sources (Ikemen GO's source, and a real file's raw bytes) agree, giving high confidence in this layout.

**Rejected alternatives:**
- *Mirror v1's exact subheader layout (2-byte Group/Sample + reserved) for v2 too, purely for internal consistency with the sibling read path* — rejected: it would not match Ikemen GO's actual behavior or real files, defeating the entire point of a "v2 read path" and reproducing a bug knowingly instead of avoiding it in the code being written now.
- *Silently fix `ParseV1` in the same change* — rejected: v1 is a closed, shipped item; changing its behavior without a dedicated ticket, tests, and Product-Owner-visible changelog entry for that specific fix risks an undocumented behavior change slipping in as a side effect of unrelated work. Flagged as a new backlog item instead.
